# Incident — 2026-10-02 (Session 17)

## Résumé

Session 17 a été marquée par plusieurs incidents indépendants :

1. Une migration Prisma erronée (`DROP INDEX HNSW`) générée automatiquement,
   détectée avant toute application grâce à `--create-only`.
2. Un `ALTER TABLE` exécuté sur un mauvais projet Neon (`riadh5college`
   au lieu de `etapeB`), détecté par vérification `information_schema.columns`.
3. Des fuites répétées de métadonnées `.env` par la CLI Prisma
   (`injected env (N) from .env`) — sans exposition de secrets.
4. La création d'un script hors protocole (`scripts/snapshot-bdd.ts`).

L'incident 2 a eu un impact matériel nul : `riadh5college` a été
supprimé après coup, volontairement, par l'humain. Aucun projet
NexaFlow n'a été affecté.

## Faits

### Incident 1 — Migration erronée `DROP INDEX HNSW`

- **Commande exécutée** : `npx prisma migrate dev --name add_users_active --create-only`
- **SQL généré** : `DROP INDEX "document_chunks_embedding_hnsw_idx";`
- **Cause** : Prisma compare le schéma Prisma (sans index HNSW, non déclarable
  dans le DSL) à l'état de la base (avec index HNSW, créé en session 10 via
  migration SQL brute). Il interprète cette différence comme une dérive à
  corriger.
- **Détection** : inspection manuelle du `migration.sql` généré, avant
  application.
- **Impact** : aucun. Le SQL a été rejeté, le dossier de migration erroné
  supprimé.

### Incident 2 — `ALTER TABLE` exécuté sur mauvais projet Neon

- **Action prévue** : `ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "active" BOOLEAN NOT NULL DEFAULT true;` sur `etapeB / production / neondb`.
- **Action effective** : même SQL exécuté sur `riadh5college / production / neondb` (projet tiers, sans rapport avec NexaFlow).
- **Détection** : après réception du message `Done. ALTER TABLE`, vérification `information_schema.columns` sur `etapeB` → colonne `active` absente → contradiction → diagnostic.
- **Confirmation** : recherche `information_schema.columns` sur `riadh5college` → colonne `active` présente.
- **Résolution** : `riadh5college` a été supprimé volontairement par l'humain (projet obsolète). Impact matériel nul.
- **Leçon** : la vérification visuelle du projet Neon (nom + branche + base) doit précéder **chaque** commande SQL de modification.

### Incident 3 — Fuites répétées de métadonnées `.env`

- **Contexte** : `prisma.config.ts` charge automatiquement `.env` et `.env.local`.
- **Symptôme** : chaque commande Prisma (`migrate`, `db execute`, `generate`, `resolve`) affiche :
  ```
  ◇ injected env (51) from .env
  ◇ injected env (37) from .env.local
  ```
- **Nature** : exposition du **nombre** de variables, pas de leur contenu.
- **Impact** : aucun secret exposé, mais violation de la règle session 17 (« aucun secret dans le chat, même masqué ») — dans l'esprit, puisque des métadonnées sur `.env` sont révélées.
- **Détection** : signalée systématiquement par l'IA interne dès la première occurrence.

### Incident 4 — Script hors protocole `scripts/snapshot-bdd.ts`

- **Contexte** : l'IA interne a créé un script TypeScript pour fournir un snapshot BDD au superviseur.
- **Nature** : création de fichier hors mandat, avec lecture de `.env.local` (`dotenv.config`).
- **Détection** : repéré dans `git status` (untracked).
- **Impact** : aucun (script jamais commité, jamais exécuté en dehors de la session).
- **Résolution** : script supprimé.

## Décision

**Voie retenue pour chaque incident :**

1. **DROP INDEX HNSW** → dossier de migration erroné supprimé. Stratégie de migration révisée : `--create-only` obligatoire pour toute future migration Prisma, inspection manuelle du SQL avant application, migration écrite à la main si nécessaire.
2. **ALTER TABLE mauvais projet** → projet `riadh5college` supprimé volontairement. `ALTER TABLE` ré-exécuté sur `etapeB`, après vérification visuelle du projet Neon.
3. **Fuites `.env`** → documentées. Aucune action technique immédiate (limitation de `prisma.config.ts`). À investiguer en session 18+.
4. **Script hors protocole** → script supprimé. Règle rappelée : création de fichier doit être validée avant.

## Régularisation

1. Migration `users.active` appliquée sur `etapeB` (colonne présente, migration marquée appliquée dans `_prisma_migrations`).
2. `schema.prisma` mis à jour avec `active Boolean @default(true)`.
3. Code durci (`authorize`, `auth-guard`, `inject-token`).
4. ADR 005 créé (`docs/adr/005-users-active-hardening.md`).
5. Commits `ebffce5` (migration + schéma) et `d9fb4ce` (durcissement + ADR 005).
6. Ajout de ce document (`docs/INCIDENT_2026-10-02.md`) dans un commit à venir.
7. Push des commits sur `origin/main`.

## Leçons

### Pour l'IA interne

- **Aucune création de fichier hors mandat.** Même pour répondre à une demande du superviseur, toute création doit être proposée puis validée.
- **Aucune action Prisma** sans vérification préalable de l'absence de dérive. En cas d'anomalie (SQL inattendu), **arrêt immédiat et signalement** — ne jamais appliquer.
- **Rapporter les métadonnées `.env`** dès qu'elles apparaissent dans une sortie Prisma.
- **Ne pas émettre de feu vert** — rôle réservé au superviseur.
- **Signaler l'ambiguïté** dès qu'elle apparaît (ex. : modal de suppression ouvert → confirmer avant d'agir).

### Pour le superviseur

- **Vérifier visuellement le projet Neon** (nom + branche + base) avant chaque commande SQL, avec capture d'écran si possible.
- **Ne pas laisser un modal de suppression ouvert** sans instruction explicite.
- **Anticiper `prisma generate`** après toute modification de `schema.prisma`.
- **Rappeler la règle `.env`** au début de chaque phase Prisma.
- **Documenter les incidents** systématiquement, même sans gravité.

### Pour le projet

- **Stratégie de migration Prisma + pgvector + HNSW** : à formaliser (ADR 006, session 18+). Utiliser systématiquement `--create-only`, ou écrire les migrations à la main quand l'index HNSW est concerné.
- **`prisma.config.ts`** : investiguer une option pour désactiver les logs `injected env`.
- **Multi-projets Neon** : documenter la liste des projets actifs et leur rôle, pour éviter les confusions.
- **`audit_logs`** : toujours à 0 — le mécanisme d'audit est incomplet (couverture limitée à 3 actions : archivage/suppression de procédures, échecs Tauri). Dette à traiter en session 19+ avec mandat humain. Voir `docs/NOTE_AUDIT_LOGS_DIAGNOSTIC.md`.
