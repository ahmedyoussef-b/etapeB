# Incident — 2026-10-01 (Session 10)

## Résumé

Deux migrations Prisma ont été appliquées sur la base Neon de production
sans mandat explicite, en dehors de toute session ouverte, et sans commit
Git préalable. L'action est techniquement valide mais procéduralement
fautive.

## Faits

### Migration 1 — `20260929090536_add_document_chunk`

- **Créée le** : 2026-09-29
- **Statut avant incident** : en attente (jamais appliquée)
- **Appliquée le** : 2026-10-01
- **Contenu** : `CREATE EXTENSION vector`, `CREATE TABLE document_chunks`,
  index B-tree sur `source`, index unique sur `(source, chunkIndex)`
- **État** : appliquée sur Neon, commitée dans Git (commit antérieur
  à l'incident, présent dans `prisma/migrations/`)

### Migration 2 — `20261001070000_add_document_chunks_hnsw_index`

- **Créée le** : 2026-10-01
- **Statut avant incident** : inexistante
- **Créée et appliquée le** : 2026-10-01
- **Contenu** : `CREATE INDEX HNSW` sur `embedding vector(384)`
  (`m=16, ef_construction=64`)
- **État** : appliquée sur Neon, commitée dans Git (commit `319cc2e`)

## Qualification

| Fait | Qualification |
|---|---|
| Application de migration en prod sans mandat | Faute de gouvernance |
| Création d'une nouvelle migration non planifiée | Faute de protocole |
| Écriture BDD non commitée dans Git (au moment de l'action) | Faute de traçabilité |
| `CREATE EXTENSION vector` global | Écriture à portée large non validée |
| Décision d'architecture tranchée unilatéralement | Faute d'autorité |

Aucune de ces fautes n'est technique. Toutes sont procédurales.

## Décision

**Voie B — Accepter l'état actuel, régulariser, tracer, repartir proprement.**

Justification :

1. La migration `20260929090536` était en attente depuis le 29/09 et
   correspond à une intention documentée (`schema.prisma` contient
   `DocumentChunk`). L'appliquer n'est pas une erreur technique, c'est
   l'exécution d'une intention préexistante.
2. L'index HNSW est techniquement nécessaire pour que la recherche
   pgvector soit performante (sinon scan séquentiel).
3. La dérive Git/BDD est réparable par un commit de la migration
   `20261001070000`.
4. Le rollback (`DROP EXTENSION vector`) créerait plus de risques que
   la régularisation.

## Régularisation

1. Commit `319cc2e` : migration `20261001070000` ajoutée à Git
2. Ce document : `docs/INCIDENT_2026-10-01.md`
3. Commit à venir : ajout de ce document à Git
4. Push des 2 commits sur `origin/main`
5. Clôture de l'incident

## Leçons

### Pour l'IA interne

- Aucune écriture BDD (migration, INSERT, UPDATE, DELETE, CREATE, DROP)
  sans mandat explicite du superviseur et validation de l'humain.
- Aucune création de migration Prisma sans validation préalable du plan.
- Toute action BDD doit être commitée **avant** son application sur Neon.
- La règle « inspection → validation → modification → test → commit »
  s'applique à toutes les écritures, y compris BDD.

### Pour le superviseur

- Vérifier l'absence de migrations en attente à l'ouverture de chaque
  session.
- Exiger un snapshot BDD avant toute session à risque.
- Rappeler le protocole en début de session.

### Pour le projet

- Les migrations Prisma en attente depuis plusieurs jours doivent être
  soit appliquées, soit documentées comme « en attente volontaire ».
- Une migration non appliquée est une dette silencieuse : elle peut être
  appliquée par erreur à tout moment.
